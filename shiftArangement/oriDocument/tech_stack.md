# 微信小程序技术栈推荐

## 1. 推荐结论

本项目建议采用 **微信原生小程序 + TypeScript + 微信云开发 CloudBase + 云数据库 + 云函数** 作为 MVP 技术栈。

这个组合最适合当前阶段：前端页面已经以移动端 HTML 原型为主，业务目标明确但团队规模和交付复杂度需要控制。微信原生小程序可以最大限度减少跨端框架带来的适配成本，云开发可以快速提供登录、数据库、文件存储、云函数和权限控制能力，整体简单、稳定、部署链路短，适合排班管理这类校内轻量业务系统。

## 2. 前端技术栈

| 层级 | 推荐技术 | 说明 |
|---|---|---|
| 小程序框架 | 微信原生小程序 | 使用 WXML、WXSS、TypeScript/JavaScript，兼容性最好，学习和调试成本低 |
| 开发语言 | TypeScript | 为用户、班次、排班、换班、加班等核心对象提供类型约束，降低后期维护风险 |
| UI 组件库 | WeUI for 小程序 + 少量自定义组件 | 表单、弹窗、按钮、Toast、Dialog 等使用成熟组件；排班表、时间格子、底部导航自定义 |
| 状态管理 | 页面级状态 + 全局 App Store 简化封装 | MVP 不建议引入复杂状态库，用户信息、角色、当前学期、当前收集任务可放在轻量全局状态中 |
| 样式方案 | WXSS + 设计 Token | 将 DESIGN.md 中颜色、字号、间距、圆角沉淀为统一变量，复用现有页面视觉规范 |
| 图标 | 微信内置图标 / WeUI 图标 / 自定义 iconfont | 替代当前 HTML 中的 Material Symbols，保证小程序内稳定显示 |

### 前端页面建议

按设计文档拆成两个角色入口，但共用底层组件：

- 公共页面：登录、注册、等待认证、忘记密码
- 助理端：填报、日程、团队、我的
- 管理端主页面：排班、日程、团队、个人/系统设置

管理端建议保持和助理端一致的四栏底部导航结构，避免管理端入口过多导致使用负担。二级页面由对应主页面进入：

- 排班页作为管理端主页：发布收集、查看进度、生成排班，并导向收集详情页、排班结果页、填报页。
- 日程页：查看本人当日与未来值班安排，发起换班、提交加班，并导向导出页/弹窗、换班与加班审核页。
- 团队页：查看团队成员与班次数统计，管理端可扩展成员维护、认证审核、角色权限。
- 个人/系统设置页：配置默认空闲时间、工作日、班次、教学周、账户安全。

## 3. 后端技术栈

| 层级 | 推荐技术 | 说明 |
|---|---|---|
| 后端平台 | 微信云开发 CloudBase | 免服务器运维，天然适配微信小程序登录和调用链路 |
| 数据库 | 云开发数据库 | 存储用户、空闲时间、收集任务、班次、排班结果、换班、加班、操作日志 |
| 业务逻辑 | 云函数 Node.js + TypeScript | 排班生成、权限校验、导出、审批、状态流转放在云函数中，避免前端绕过规则 |
| 文件存储 | 云存储 | 保存导出的排班表图片、Excel 文件、分享用临时文件 |
| 定时任务 | 云函数定时触发器 | 创建每周收集任务、提醒未填报用户、归档历史任务 |
| 消息通知 | 微信订阅消息 | 用于填报提醒、认证结果、换班审批、排班发布通知 |

### 为什么不优先推荐自建后端

自建后端如 Spring Boot、NestJS、MySQL、Redis 更适合中大型系统，但本项目当前主要目标是微信小程序 MVP。若从一开始自建后端，会增加服务器、域名、HTTPS、备案、鉴权、安全、部署监控等成本。CloudBase 能更快闭环产品验证。

## 4. 数据库设计建议

建议使用云数据库集合：

| 集合 | 用途 |
|---|---|
| users | 用户账号、角色、认证状态、学院、年级、成员标签 |
| semesters | 学期、教学周、年级更新状态 |
| shift_templates | 默认班次配置，如 08:30-13:00、13:00-17:30 |
| availability_collections | 每周空闲时间收集任务 |
| availabilities | 用户按日期、班次提交的空闲状态 |
| schedules | 排班结果，含人员、状态、风险标签 |
| swap_requests | 换班申请和审批状态 |
| overtime_records | 加班记录和审核结果 |
| operation_logs | 管理员操作记录，MVP 可记录关键操作 |
| system_settings | 全局配置，如工作日、默认每班人数、规则开关 |

### 数据建模原则

- 用户权限必须以后端云函数校验为准，前端只负责展示。
- 排班结果建议保留历史快照，避免修改教学周或班次配置后影响历史数据。
- 管理端手动调整排班后，应记录 `updated_by`、`updated_at` 和调整原因。
- MVP 可采用“最后保存为准”，但需要写入操作日志，便于后续追溯。

## 5. 排班算法实现建议

排班生成不建议放在小程序前端，应放入云函数。

MVP 可先使用规则评分算法：

1. 先过滤硬性条件：用户有空、未超过每周最高排班数、账号 active、班次需要值班。
2. 对候选人打分：低排班次数优先、老带新优先、跨学院优先、跨年级优先、性别搭配优先。
3. 按班次逐个生成建议结果。
4. 对无法满足规则的班次写入风险标签，如 `无人可排`、`人数不足`、`新人单独值班`。
5. 管理员在前端手动调整，云函数重新校验风险。

这种方案比一开始引入复杂优化算法更简单，也足够支撑设计文档中的 MVP。后续如排班规模变大，可以再升级为约束求解或线性规划。

## 6. 导出与分享方案

设计文档中提到 Excel、图片或小程序内可查看链接。建议 MVP 这样处理：

| 能力 | MVP 推荐 |
|---|---|
| 小程序内查看 | 优先实现，排班发布后所有相关用户可在日程页查看 |
| 分享到微信群 | 使用小程序页面分享，分享排班结果页 |
| 生成图片 | 管理端提供“生成排班图片”，由云函数或前端 canvas 生成后保存云存储 |
| Excel 导出 | 管理端 P0/P1 实现，云函数生成 xlsx 并上传云存储 |
| PDF/Word | 暂不做，放到后续版本 |

推荐优先级：**小程序内查看 + 分享页面 > 生成图片 > Excel > PDF/Word**。

## 7. 工程化与质量保障

| 能力 | 推荐方案 |
|---|---|
| 代码规范 | ESLint + Prettier |
| 类型检查 | TypeScript strict 模式逐步开启 |
| 单元测试 | 排班算法云函数使用 Jest/Vitest |
| 端到端测试 | MVP 可先人工测试关键流程，后续引入 miniprogram-automator |
| 环境隔离 | CloudBase dev / prod 两套环境 |
| 配置管理 | 不把密钥写入前端，敏感逻辑统一放云函数 |
| 版本管理 | Git，按功能分支开发 |

## 8. 从现有 HTML 原型迁移建议

现有 HTML 页面可以作为视觉和交互原型使用，但不建议直接尝试转译。更稳妥的方式是：

1. 抽取现有页面的结构：顶部栏、底部导航、卡片、时间格子、弹窗。
2. 将 Tailwind 样式转换成 WXSS 设计 Token 和组件样式。
3. 将静态数据替换为 service 层调用云函数或云数据库。
4. 先完成 P0 页面闭环，再补 P1 的换班、加班和权限转移。

## 9. MVP 开发顺序建议

1. 搭建微信原生小程序 + CloudBase 项目。
2. 实现登录、注册、认证、角色分流。
3. 实现用户集合、成员管理、管理员认证审核。
4. 实现教学周、工作日、默认班次配置。
5. 实现空闲时间收集发布与助理填报。
6. 实现管理端收集进度和可排人员详情。
7. 实现排班生成云函数和风险标签。
8. 实现排班结果人工调整、确认、发布。
9. 实现助理端和管理端日程查看。
10. 实现排班分享页和图片/Excel 导出。

## 10. 最终推荐版本

```text
前端：微信原生小程序 + TypeScript + WXML + WXSS + WeUI
后端：微信云开发 CloudBase + 云数据库 + 云函数 Node.js/TypeScript
文件：云存储
通知：微信订阅消息
导出：云函数生成图片/Excel，文件存入云存储
测试：Jest/Vitest 测试排班算法，人工测试小程序主流程
```

这个技术栈的核心优势是：简单、微信生态适配好、部署成本低、权限和业务逻辑可以集中在云函数中，足够支撑设计文档中的 MVP，并且后续仍能平滑扩展到更复杂的排班算法和统计能力。
